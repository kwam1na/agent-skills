# Wait for, and gate on, every AI review a PR gets

Epic V26-3344. run-delivery waits for exactly one pipeline reviewer. `review.pr` is `{author, waitSeconds}`, and `pr_review_state` in
`skills/run-delivery/scripts/run_delivery.py` keeps the PR comment whose author display name equals `author`. That comment counts as
current when it was updated no earlier than the latest check at the head. An outside adopter's PRs (3478 to 3504) get two AI reviews as
parallel pipeline steps that run with failures ignored, and only one of them is read. What that leaves:
- The second reviewer is never waited for or triaged.
- A lane can defer a finding the gating reviewer blocks on and still be accepted, though the PR can't merge without that reviewer's
  approval.
- Freshness is a timestamp guess. With overlapping pipelines, a review of an older head passes as current.
- A reviewer step that fails leaves the pipeline green, so the wait runs its full `waitSeconds` and stops with nothing to act on.
- One transient forge error ends the wait. The Bitbucket adapter has no retry, and `call_adapter` stops on any non-zero exit.
- Matching by display name breaks on a rename, or matches another bot posting under the same name.

Everything here is in `skills/run-delivery/`: `run_delivery.py` (`pr_review_config`, `pr_review_state`, `pr_review`, `handoff`,
`lead_accept`, `pr_review_text`, the doctor's `review_pr`, and the `pr-review-current` reviewGate), both forge adapters' `reviews`, the
lane-brief template and the references. The adopter's side, reviewers that post Code Insights reports and the adopter's own
configuration, is tracked in the adopter's tracker.

The delivery runs on its own integration branch, `integrate/pr-reviewers`, cut from `main` at `fa1f09f`, so that it doesn't collide
with deliveries already in flight on `main` (V26-3406 among them, whose lane 2 owns the same `skills/run-delivery/` files). The
binding's `bases` already serves `integrate/*`. The branch is merged into `main` once those deliveries have landed (Decision 11).

The items are V26-3345 to V26-3348, already in Linear under the epic. Each story's criteria below are the tracker item's, word for
word, with the decisions that settle what they leave open. V26-3349, the reviewer re-run grant, stays in Backlog, outside this plan.

## Decisions

1. **The configuration.** `review.pr` takes either the legacy `{author, waitSeconds}` or
   `{waitSeconds?, settleSeconds?, reviewers: [...]}`. Each reviewer is `{id, account?, author?, signature?, required, gate?, report?}`.
   `id` matches `^[a-z][a-z0-9-]*$` and is unique. A reviewer needs `account` or `author`. `required` is a boolean, and absent means
   `true`. `gate` is `"approval"` or `"verdict"`, and `report` is a non-empty string. `settleSeconds` defaults to 300 and `waitSeconds`
   to 1800, both non-negative integers. Any other member, a duplicate `id`, or a list with no reviewer is refused by every command that
   reads the configuration, and by the doctor's `review_pr` row as `wrong`, naming the reviewer and the member. The legacy shape is read
   as one required reviewer `{id: "review", author}` with no `account`, `signature`, `gate` or `report`, and with the settle rule off
   (Decision 4). The doctor warns, without failing, about a reviewer with neither `account` nor `signature`, since a display name alone
   can match another bot.
2. **Matching.** A comment belongs to a reviewer when its `account` equals the reviewer's `account`, if set, and otherwise when its
   `author` equals the reviewer's `author`. When `signature` is set, the comment's body must also contain it, as plain text. Among a
   reviewer's matching comments the latest by `at` is its review. One comment can match more than one reviewer only if their
   configurations overlap, and that is the adopter's configuration to fix. The doctor warns when two reviewers have the same `account`
   or `author` and neither has a `signature`.
3. **Freshness, without a report.** A reviewer's review is current when every check at the head has passed and the review's `at` is no
   earlier than the latest check's `at`, as today. A failed check refuses at once, as today.
4. **The poll and the settle.** Each poll classifies every reviewer as `pending`, `current`, `absent` or `silent`. Once every check at
   the head has passed, the settle starts at the latest check's `at`, read from the forge, and ends `settleSeconds` later by the local
   UTC clock. After the settle, an optional reviewer with no current review is `absent`, and a required one is `silent` (V26-3347).
   Before the settle, or while any check is pending, a reviewer with no current review is `pending`. The wait ends when no reviewer is
   `pending`, or at its deadline. The settle runs with or without `--wait`: without it, `pr-review` reads once and reports what that
   read shows. The legacy shape has no settle: its one reviewer is `pending` until current, as today.
5. **What the adapters return.** `reviews` adds, for each comment, `account`: Bitbucket's `user.uuid`, GitHub's `author.login`. It adds
   `approvals`: `[{account, name, at, commit?}]`, from Bitbucket's participants with `approved: true` (`participated_on`, no commit) and
   from GitHub's reviews in state `APPROVED` (`submittedAt`, `commit.oid`). It adds `reports` (V26-3348, Decision 9). A member an older
   or custom adapter doesn't return is read as empty, so the legacy configuration needs none of them. A configuration that uses
   `account`, `gate: "approval"` or `report` with an adapter whose `reviews` returns no such member refuses, naming the member, rather
   than matching nothing.
6. **Retries.** An adapter reports a transient failure by exiting 75 (`EX_TEMPFAIL`): a timeout, a connection error, or an HTTP 5xx or
   429. Both reference adapters do so; any other failure keeps exit 1. `call_adapter` raises a transient refusal for exit 75, and only
   the polling loops in `pr-review --wait` and `pr-review-current --wait` retry it, with backoff starting at 5 seconds and doubling to
   at most 60, until the wait's deadline. At the deadline the last transient error is the refusal. Every other forge call, and a 4xx,
   refuses at once. This applies to the legacy configuration too: the only behaviour it changes is a wait that used to end on a
   transient error and now keeps waiting, which is the fix the epic asks for. `config.md` documents exit 75 for a `forge.argv` adapter.
7. **The record.** `pr-review.json` becomes `{schema: "pr-review/2", head, url, reviewers: {<id>: {state, required, author?, account?,
   at?, body?, report?, gate?}}}`, where `state` is `current` or `absent`, and `gate` is `{kind, met, why}`. The hand-off writes each
   current review's triage into its entry. `lead-accept` also reads the old shape, a single `{head, url, author, at, body, triage}`, as
   reviewer `review`, so a lane that recorded on an older generation is still checked. `pr-review` makes the `pipeline-green` review
   move once every required reviewer is current, as it does today for the one.
8. **Triage.** `handoff --pr-review-triage` is repeatable. `ID=TEXT` names a reviewer; a bare `TEXT` is accepted only when exactly one
   review is current, and is that one's. Every current review needs one, and an absent reviewer takes none. A triage for an unknown or
   absent id is refused. The hand-off message shows each.
9. **Reports (V26-3348).** Bitbucket's `reviews` returns the reports at `--head` from `/commit/{head}/reports`:
   `[{id: external_id, result, at: updated_on, data: [{title, type, value}]}]`, with `result` one of `PASSED`, `FAILED`, `PENDING`. The
   GitHub adapter returns `reports: null`, and a reviewer with `report` under the GitHub adapter is refused by the doctor and by every
   command, naming Bitbucket as the forge that has reports. With `report` set, a reviewer is `current` exactly when its report exists at
   the head with result `PASSED`, whatever the checks and timestamps say, and its comment is then read for its text, the latest matching
   one. `PENDING`, or no report yet, is `pending` until the settle, then `silent` or `absent` as in Decision 4. A `FAILED` report is
   `silent` at once, with the refusal saying the reviewer errored. A current report with no matching comment refuses, saying the report
   names a review that wasn't posted.
10. **Gates (V26-3346).** `"verdict"`: the verdict is the report's data item titled `Verdict` (case-insensitive) when there is a report,
    and otherwise the review body's first line matching `^\*\*Verdict:\*\*\s*(.+)$`. It is met when that value's first word, lowercased
    with punctuation stripped, is `approve` or `approved`; otherwise unmet, naming the value, or saying the verdict is missing.
    `"approval"`: with a report, it reads the report's result and verdict in its place, as the verdict gate does, since a report is tied
    to the commit. Without one, it is met when the reviewer's `account` is among the approvals, and where an approval names a `commit`,
    that commit is the head. A reviewer with `gate: "approval"` and no `account` is refused by the configuration check. Bitbucket ties no
    approval to a commit, so there an approval of an earlier head counts. `config.md` says so in a sentence, which is criterion 4's
    "the docs say which applies". A gate is checked only on a current review: an absent optional reviewer's gate is not checked.
11. **The integration branch and its merge.** Lanes branch from, and the queue merges into, `integrate/pr-reviewers`. The delivery file,
    plan, brief and notes are committed there, not on `main`. Lanes never merge `main` in. The lead merges `main` into the branch only
    when the final merge needs it, and then re-runs the gates there. The merge into `main` happens once V26-3406 and every other
    delivery in flight on `main` at approval has landed or closed. It is one merge commit by the lead, pushed after the full suite
    passes on it locally on macOS with Python 3.11. The operator granted that merge on 2026-11-11 when approving this delivery. Conflicts
    in `skills/run-delivery/` are resolved by the lead against both sides' tests, and `provenance.lock.json` by the writer.
12. **Tests.** New rows go in a new module, `tests/test_run_delivery_pr_review.py`, so the integration merge doesn't collide with
    `tests/test_run_delivery.py`, which V26-3406's lane 2 owns on `main`. The existing PR-review rows stay where they are, and change only
    where a criterion changes what they assert. Adapter rows go in `tests/test_forge_adapters.py`. Every row drives a fixture adapter
    through `forge.argv` or a fake HTTP layer. No row reaches a real forge or sleeps for real, so the poll interval, backoff and clock are
    injectable.

## Stories

### V26-3345. Read several PR reviewers, each required or optional

Lane 1, tier 1, not blocked. Test-first, per Decisions 1 to 8 and 12. Before any behaviour changes, characterization rows pin the
legacy configuration's printed text, refusals, record and exit codes for `pr-review`, `handoff`, `lead-accept` and `pr-review-current`.
Files: `skills/run-delivery/scripts/run_delivery.py`, `skills/run-delivery/adapters/forge_bitbucket.py`,
`skills/run-delivery/adapters/forge_github.py`, `skills/run-delivery/templates/lane-brief.md`, `skills/run-delivery/SKILL.md`,
`skills/run-delivery/references/config.md`, `skills/run-delivery/references/adopting.md`, `tests/test_run_delivery_pr_review.py` and
`tests/test_forge_adapters.py`.

Acceptance criteria:
1. Each reviewer is matched by `account` (the forge's account id, which both adapters' `reviews` now return) when set, else by `author`,
   and in either case by `signature` in the body when set. The doctor warns when a reviewer has neither `account` nor `signature`, and
   refuses duplicate `id`s.
2. Each poll classifies every reviewer as `pending`, `current` or (optional only) `absent`: absent once checks passed and no matching
   comment arrived within `settleSeconds` (default 300). The wait ends when no reviewer is pending. A failed check refuses at once, as
   today.
3. `pr-review.json` holds every reviewer's review or `absent`. `pr-review` prints each under its `id`, and makes the review move once
   every required one is current.
4. `handoff --pr-review-triage ID=TEXT` is repeatable and required for each current review; a bare `TEXT` still works when exactly one
   is current.
5. `lead-accept` and `reviewGate` check every required reviewer is current, triaged and unchanged. An optional reviewer recorded absent
   that is now current sends the lane back to read it.
6. A forge call inside the wait is retried with backoff on a timeout, a connection error or a 5xx, until the wait's deadline. A 4xx
   still refuses at once.
7. The legacy config behaves exactly as today. `config.md`, `adopting.md`, `SKILL.md` and the lane-brief text describe the list.

Settled by the decisions:
- `reviewGate` runs in the queue's checkout, which holds no lane record, so it checks what it can see there: every required reviewer is
  current, and its gate, once V26-3346 lands, is met. Triage and "unchanged" are `lead-accept`'s, and the queue merges only accepted
  candidates.
- Until V26-3347, a required reviewer past the settle stays `pending`, as today.
- Criterion 6 is Decision 6, with 429 counted as transient. Criterion 7's "exactly as today" holds apart from Decision 6's retry.
- The old record shape is read by `lead-accept` (Decision 7).

Sensors: `tests/test_run_delivery_pr_review.py`, `tests/test_run_delivery.py`, `tests/test_forge_adapters.py`,
`tests/test_merge_queue.py`, `scripts/validate-registry.py`.

### V26-3346. Gate a PR reviewer on its approval or its verdict

Lane 1, tier 1, after V26-3345. Test-first, per Decisions 5 and 10. Files: as V26-3345's.

Acceptance criteria:
1. A reviewer takes `gate`: `"approval"` (the reviewer's account has approved the PR), `"verdict"` (the review's `**Verdict:**` line
   says approve), or absent (no gate, as today).
2. Both adapters' `reviews` also return the PR's approvers (account id, display name, when).
3. With a gate unmet, `pr-review` says so beside the review, `handoff` refuses with the reviewer's `id` and what it needs (fix and push,
   so the reviewer runs again), and `lead-accept` and `reviewGate` refuse the same way.
4. An `"approval"` gate is only as fresh as the forge makes it: Bitbucket doesn't tie an approval to a commit. Where the reviewer posts a
   report at the commit (the Code Insights story in this epic), the gate reads the report's result there instead of the PR's approvals.
   The docs say which applies.
5. A `"verdict"` gate on a review with no verdict line is unmet, and says the line is missing.

Settled by the decisions: criterion 4's report path lands with V26-3348, which adds a row for it here. Until then a reviewer with
`report` is refused as Decision 9 says. A reviewer with `gate: "approval"` and no `account` is refused by the configuration check.

Sensors: as V26-3345's.

### V26-3347. Stop the PR-review wait when a required reviewer posts nothing after a green pipeline

Lane 1, tier 1, after V26-3346. Test-first, per Decision 4. Files: as V26-3345's.

Acceptance criteria:
1. Once every check at HEAD passed, a required reviewer with no current review after `settleSeconds` stops the wait with: the pipeline
   is green at <head> but <id> posted nothing since; re-run its step or ask the lead.
2. The stop is a distinct refusal the lane brief tells the lane to escalate (blocked, to the lead), not to retry the wait.
3. `--wait` without the settle having passed keeps waiting as today; a reviewer still running (where its report or step is visible as in
   progress) is not treated as silent.

Settled by the decisions:
- The distinct refusal exits 3, where every other run-delivery refusal exits 2. Its stderr line starts `run-delivery: silent reviewer`.
  `pr-review-current` exits 3 for it too.
- The lane brief's PR-review paragraph tells the lane to hand off blocked on it with `--blocked pr-review=<the line>`, and not to run
  the wait again.
- The legacy shape has no settle, so it never stops this way (Decision 4).
- "A step visible as in progress" is a pending check, which keeps every reviewer `pending`. The report half lands with V26-3348.

Sensors: as V26-3345's.

### V26-3348. Read each PR reviewer's Code Insights report at the commit it reviewed

Lane 1, tier 1, after V26-3347. Test-first, per Decisions 5, 9 and 10. Files: as V26-3345's.

Acceptance criteria:
1. A reviewer takes an optional `report` (the report's `external_id`). The Bitbucket adapter's `reviews` returns the reports at `--head`
   (`/commit/{sha}/reports`): external id, result, created/updated time, and its data fields. The GitHub adapter maps check runs the same
   way, or says it can't.
2. With `report` set, the reviewer is current exactly when its report exists at HEAD; the comment is then read only for its text to
   triage. A FAILED report result means the reviewer errored, and stops the wait as the silent-reviewer story does, at once rather than
   after the settle.
3. The report's data carries the verdict; the `"verdict"` gate reads it from there when present.
4. Without `report`, the comment-and-timestamp rule stays as it is.
5. `adopting.md` documents the report contract: external id, result PASSED once the review is posted (whatever its verdict), FAILED when
   the reviewer errored, verdict in data.

Settled by the decisions:
- The GitHub adapter says it can't (Decision 9).
- "Exists" means exists with result `PASSED`. A `PENDING` report is the "visible as in progress" case of V26-3347's criterion 3, and
  stays `pending` until the settle.
- A current report with no matching comment refuses.
- V26-3346's criterion 4 gains its report row here.

Sensors: as V26-3345's.
