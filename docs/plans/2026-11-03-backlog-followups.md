# Deliver the follow-ups from tag-driven releases

Six tickets, each with its own scope and acceptance criteria in the tracker, delivered under one epic. The tickets are binding for what
each one does. This plan decides only what they cannot: order, file ownership and how the work reaches `main`.

## Finish line

- Each ticket is merged to `main` on a green full local run on macOS with Python 3.11, and `main`'s CI on the merged commit passes on the
  Ubuntu job and `cut-release`, with the run linked.
- Every deferral has a follow-up item, and the epic and its items are closed with this evidence.

## Out of scope

Windows validation and the scheduled Linear connector check, by the operator's word. The parked mechanical-duties epic and the standalone
adoption-gap tickets. A release is cut only on the operator's word.

## Decisions

- **Three lanes.** A takes V26-3051, then V26-3050. B takes V26-3082, then V26-3078. C takes V26-3077, then V26-3076.
- **How it reaches `main`.** Tiers 1 to 3 land on `delivery/backlog-followups` through the queue, and reach `main` through one integration
  change with the delivery's binding removed. V26-3050 needs a tag holding V26-3051 to install, so it starts from `main` after that
  integration and goes straight into `main`, since it adds the standing binding.
- **Version.** Tracker profiles gaining a skill is additive under `AGENTS.md`'s rule, so the next version is a minor. V26-3082's item 13 and
  V26-3050 touch `AGENTS.md` in sequence, not together.
- **Gate at each hand-off.** A unit's own sensors in the lane, the queue's selected checks, and the full local macOS run on Python 3.11 at the
  integration. Local runs use four workers at most, and nobody uses `pkill` or `killall`.
- **Item 3 of V26-3082 and the lens brief.** The stopping rule reaches a lens through `review-work` or `obtain-review`, which that ticket owns.
